# دليل اختبار Restaurant WiFi Control V9.2 Beta — إنترنت داخل عبر Wi-Fi

**هذه نسخة تجريبية وليست نظام تحكم تجاري بالإنترنت.** هذه النسخة تساعد على
التحقق من التوصيل والتعرف على كروت الشبكة، وتسمح بتجربة *حجب مرور IPv4*
لمدة دقيقتين في شبكة اختبار معزولة، بناءً على نموذج WFP السابق. يجب عدم
استخدامها على شبكة عملاء أو أثناء الاعتماد على اتصال حيوي.

## التوصيل على جهاز الاختبار

```text
الراوتر ---- Wi-Fi ----> كمبيوتر Windows 10/11
                             |
                             +--- كابل Ethernet ثانٍ --> Access Point وضع AP / Bridge
                             |
                             أو
                             +--- واجهة Wi-Fi Hotspot افتراضية مختلفة --> هاتف اختبار
```

- يدخل الإنترنت إلى **الكمبيوتر عبر Wi-Fi** من الراوتر، وليس مطلوبًا كابل LAN في هذه التجربة.
- عند الخروج عبر Access Point مستقل، استخدم منفذ Ethernet آخر من الكمبيوتر إلى نقطة الوصول؛
  لا تصل نقطة الوصول مباشرة بالراوتر، وإلا قد يتجاوز العملاء الكمبيوتر.
- عند الخروج عبر Hotspot من الكمبيوتر، فعّل Mobile Hotspot من إعدادات Windows أولًا.
  يلزم أن يدعم كارت Wi-Fi والتعريف مشاركة الاتصال، وأن تظهر واجهة hotspot افتراضية منفصلة.
  كارت واحد يظهر بالمعرّف نفسه كمدخل ومخرج **غير مقبول**.
- يلزم أن يكون عنوان شبكة العملاء مختلفًا عن شبكة الراوتر (مثل
  Wi-Fi الراوتر `192.168.1.x/24`، وشبكة العملاء `192.168.137.x/24`).
- اضبط مشاركة الإنترنت ICS/DHCP يدويًا من Windows، لأن البرنامج لا يجهزهما تلقائيًا.

## خطوات أول تجربة آمنة

1. استخدم **شبكة اختبار معزولة** وهاتفًا واحدًا فقط، واحفظ أي عمل مهم قبل الاختبار.
2. ثبّت الإصدار V9.2 beta على كمبيوتر Windows x64 بصلاحية مسؤول. يجب أن تبدأ خدمة
   `Restaurant WiFi Gateway`. لا تبدأ الحجب قبل تشغيل ومراجعة الاتصال العادي.
3. افتح البرنامج ثم **الإعدادات → توصيل الشبكة**.
4. اختر **مدخل الإنترنت: Wi-Fi** المتصل بالراوتر وعليه IPv4 وDefault Gateway.
5. اختر **مخرج الإنترنت** (Ethernet للـAccess Point أو واجهة Wi-Fi Hotspot الافتراضية)
   على شبكة IPv4 أخرى **وبدون Default Gateway**.
6. اضغط **فحص المسار** ثم **حفظ الاختيارات**. هذه الخطوة لا تنشئ NAT ولا تمنع الإنترنت.
7. تحقق أولًا من اتصال هاتف الاختبار بالإنترنت في وضع Windows ICS/Hotspot المعتاد.
8. افتح على نفس الكمبيوتر `http://127.0.0.1:8765/status/`، وتحقق من اتصال خدمة Gateway.
9. إذا لم يكن هناك تداخل بالشبكات ولا احتياج لهذا الاتصال أثناء الاختبار،
   اختر **اختبار حجب IPv4 لمدة دقيقتين**، واقرأ التحذير قبل التأكيد.
10. راقب الحالة `ipv4-block-trial-active` في Gateway ثم جرّب تصفح موقع يدعم IPv4
    من **الهاتف**. قد يفشل اختبار الحجب أو يبقى المرور مسموحًا بسبب Windows/NAT/ICS أو
    خصائص عتاد الشبكة؛ نجاح بناء البرنامج لا يثبت نجاح WFP على الجهاز.
11. اضغط **إيقاف اختبار الحجب** فورًا لإيقافه مبكرًا، أو انتظر انتهاء الدقيقتين؛
    ثم تأكد من عودة التصفح من الهاتف. إذا تعذر الوصول إلى الأزرار، أوقف خدمة
    `Restaurant WiFi Gateway` من إدارة خدمات Windows؛ فمرشحات WFP التجريبية
    تستخدم جلسة ديناميكية يُفترض أن تُحذف عند إغلاق مقبضها، ويجب التحقق من ذلك عمليًا.
12. احتفظ بنص حالة `experimentalWfp` مع نسخة Windows، وأسماء مدخل/مخرج الشبكة
    ونتيجة مرور الإنترنت قبل التجربة وأثناءها وبعدها. لا تنشر كلمات المرور أو أكواد العملاء.

## الحدود المهمة

- **اختبار الحجب IPv4 فقط**؛ لا يثبت منع IPv6 ولا يعالج تجاوز المسار.
- لا يوجد توزيع ICS/NAT تلقائي، ولا تحويل تلقائي إلى بوابة الأكواد.
- **إدخال الأكواد غير مفعل على الشبكة الحقيقية**: لن يستهلك Gateway الكود دون
  متحكم دخول مثبت ومؤكد. لا يوجد تحديد سرعة أو قياس حصة بيانات حتى الآن.
- يُحفظ طلب الاختبار على خدمة Windows ويتوقف تلقائيًا بعد نافذة قصيرة.
  زر الإيقاف يعمل دون الحاجة لبقاء واجهات الشبكة متصلة.
- بناء GitHub Actions ناجح يعني أن البرنامج بُني وأن اختبارات آلية مرت،
  ولا يعني اجتياز تجربة الحجب على جهاز Windows.

## الحصول على النسخة

من صفحة GitHub Actions الخاصة بآخر تشغيل ناجح لفرع
`feature/phase1-foundation-security`، افتح قسم **Artifacts** واختر
`Restaurant-WiFi-Control-V9.2-Beta-Test`، ثم فك ضغط ملف ZIP وشغّل
`Restaurant_WiFi_Control_V9_2_Beta_Setup.exe` بصلاحية المسؤول.

**لا تختبر على شبكة الإنتاج؛ التثبيت يحدّث الخدمة الموجودة على الجهاز.**
